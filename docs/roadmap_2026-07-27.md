## Décisions du jour à ajouter au CDC

| # | Décision |
|---|---|
| **D32** | **Le bloc PE n'a jamais de seuil de pertinence.** Il s'affiche dès qu'il existe du non coté. Motif métier : peu d'actifs à forte importance individuelle, entrée souvent liée à un événement client — la part du patrimoine est la mauvaise métrique. *Clôt O13 avec les autres seuils.* |
| **D33** | Le store des référentiels est un **Postgres, dans une base séparée** de la projection du datahub. On s'inspire de ses conventions, on ne pollue pas ses tables. Cette base est la **staging du fork, côté données** — pendant exact du paquet forké côté code ; les deux convergent au même moment (M7). |
| **D34** | Le **dashboard admin est un live artifact** qui reçoit les demandes d'adjudication et écrit dans le store. Prérequis dur : un **MCP maison read/write** sur la base. Un artefact ne peut ni lire un fichier local, ni porter le store lui-même (`localStorage` est par utilisateur, donc sans partage). |
| **D35** | **Seed vendoré d'abord, promotion ensuite.** Les référentiels sont seedés dans le paquet, puis promus vers le store quand le MCP existe. La copie vendorée survit comme **snapshot de secours** (cold-start, réseau indisponible). Aucune tâche du skill n'attend l'infra. |
| **D36** | Les référentiels **cessent d'être vendorés comme source de vérité**. Le skill les lit au store à chaque run. C'est ce qui supprime le « dites aux CGP d'updater le skill » — et cela réalise par avance E4/K2 (« cible : table dont l'asset est le snapshot »). |
| **D37** | *(2026-07-28)* Le MCP des référentiels est un **serveur autonome**, pas un module greffé sur `mcp-o2s-server`. Cycle de vie et déploiement indépendants ; à la convergence datahub on débranche un serveur entier au lieu de démêler un module. Clôt **O14**. |
| **D38** | *(2026-07-28)* **Un profil de gabarit par template**, jamais un profil « fonctionnel » qui en encapsule plusieurs. Un assureur peut avoir 50 templates : il nous faut les 50. Motif : *cycler sur 50 signatures pour trouver la bonne est plus simple que maintenir un schéma unique qui ne reflète pas la réalité* — et le self-healing (A5) les fait arriver **organiquement** dans la base, un par un, au lieu d'exiger un catalogue exhaustif au seed. Clôt **O11**. |

**Contrainte d'environnement constatée** : le sandbox d'exécution n'a **aucun egress TCP brut**
(ports 443/53/5432 bloqués, DNS non résolu). Toute la voie B s'exécute côté Thomas / Code ; les
livrables produits ici sont des **fichiers à exécuter** (DDL, serveur MCP, chargeur de seed), écrits
en variables d'environnement, jamais d'identifiants en dur.

## Points de convergence

1. **A4 → B4** : le seed vendoré est la source de la promotion. Sans A4, B4 n'a rien à charger.
2. **B3 → B5** : le dashboard n'existe pas avant le MCP. C'est la seule vraie inconnue du plan.
3. **A5 ↔ B5** : les propositions de drift produites par le skill alimentent la file d'adjudication.
4. **Fin de parcours** : M7 + H4 — retour vers Code, le registre **est** l'addendum, et la base de
   staging est repliée dans `clients.meta.reference_tables`.

## Ordonnancement — ce qui est vraiment contraint

- **Un seul point bloquant** : O5 / C4 (ids provisoires Gronier), prérequis de A1. À traiter en premier.
- **Rien dans la voie A n'attend la voie B**, grâce à D35 (seed vendoré d'abord). C'est délibéré : la
  voie B porte la seule dépendance externe, on ne la met pas sur le chemin critique.
- **La voie B peut démarrer tout de suite** (B0 ne demande que des informations) et avancer en
  parallèle. Plus elle démarre tôt, plus B4/B5 arrivent sans attente.
- **A8 est volontairement tard** : depuis D20 le writer n'est plus dans le chemin de rendu.
