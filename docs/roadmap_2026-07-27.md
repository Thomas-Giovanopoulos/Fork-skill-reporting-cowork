## Décisions du jour à ajouter au CDC

| # | Décision |
|---|---|
| **D32** | **Le bloc PE n'a jamais de seuil de pertinence.** Il s'affiche dès qu'il existe du non coté. Motif métier : peu d'actifs à forte importance individuelle, entrée souvent liée à un événement client — la part du patrimoine est la mauvaise métrique. *Clôt O13 avec les autres seuils.* |
| **D33** | Le store des référentiels est un **Postgres, dans une base séparée** de la projection du datahub. On s'inspire de ses conventions, on ne pollue pas ses tables. Cette base est la **staging du fork, côté données** — pendant exact du paquet forké côté code ; les deux convergent au même moment (M7). |
| **D34** | Le **dashboard admin est un live artifact** qui reçoit les demandes d'adjudication et écrit dans le store. Prérequis dur : un **MCP maison read/write** sur la base. Un artefact ne peut ni lire un fichier local, ni porter le store lui-même (`localStorage` est par utilisateur, donc sans partage). |
| **D35** | **Seed vendoré d'abord, promotion ensuite.** Les référentiels sont seedés dans le paquet, puis promus vers le store quand le MCP existe. La copie vendorée survit comme **snapshot de secours** (cold-start, réseau indisponible). Aucune tâche du skill n'attend l'infra. |
| **D36** | Les référentiels **cessent d'être vendorés comme source de vérité**. Le skill les lit au store à chaque run. C'est ce qui supprime le « dites aux CGP d'updater le skill » — et cela réalise par avance E4/K2 (« cible : table dont l'asset est le snapshot »). |
| **D37** | *(2026-07-28)* Le MCP des référentiels est un **serveur autonome**, pas un module greffé sur `mcp-o2s-server`. Cycle de vie et déploiement indépendants ; à la convergence datahub on débranche un serveur entier au lieu de démêler un module. Clôt **O14**. |
| **D44** | *(2026-07-29)* **Aucun identifiant client dans le store des référentiels.** Ce n'est pas une précaution de conformité, c'est une règle de **confidentialité entre CGP** : `ref_bundle` rend la base **en entier à chacun**, donc tout identifiant qui y entre est visible de tous. Le défaut existait déjà en local, indépendamment de tout hébergement — les deux successions du seed portaient `contexte = "Wealins FC051727 — poche FAS"`, révélant à n'importe quel CGP qu'un client détient ce contrat. **La distinction qui tranche** : une succession est un *fait de marché* (« la poche ex-Intesa a été reprise par CA Indosuez ») ; le numéro de contrat n'est pas le fait, c'est **l'endroit où on l'a observé**, et sa place est le dossier de run du client. Trois colonnes concernées : `acteur_successions.contexte` (numéro de contrat retiré), `adjudications.source_document` (nom de fichier → empreinte du contenu + gabarit + arrêté, ce qui est **plus** utile à l'arbitre et **moins** révélateur), et les e-mails de CGP (`propose_par`, `arbitre_par`, `validated_by`) — **conservés**, car la responsabilité nominative est la contrepartie du privilège admin (D34) et il s'agit de donnée professionnelle. Cf. `infra/migration_002_purge_identifiants_clients.sql`. |
| **D43** | *(2026-07-29)* **Hébergement : MCP et Postgres sur Railway, colocalisés** — Azure Database for PostgreSQL Flexible Server reste la cible de production (RUNBOOK §4), mais on ne l'attend pas. Trois motifs. *(a)* Le MCP y est une **recopie** : `mcp-o2s-server` est déjà déployé sur Railway avec `railway.toml` (healthcheck `/health`) et `nixpacks.toml` (`uv sync --no-dev`), et le serveur des référentiels a la même forme. *(b)* Colocaliser la base supprime toute question d'egress entre les deux. *(c)* **La base est reconstructible** : `seed/seed.sql` la rejoue en une commande, donc perdre l'instance coûte les adjudications faites depuis le dernier seed, pas le référentiel — la durabilité pèse ici beaucoup moins que pour le datahub. C'est ce qui rend un hébergement léger acceptable, et c'est ce qui **débloque la démonstration du test de réussite** : « visible au run suivant d'un autre CGP » exige une base joignable, pas une base définitive. Prérequis : **D44 d'abord**. |
| **D42** | *(2026-07-29)* **La clé d'unicité des gabarits devient `(emetteur_code, gabarit, valide_depuis)`**, et la **périodicité sort du matching** pour devenir une colonne informative renseignée par le contexte (date d'arrêté, run, saisie CGP). Deux motifs, et ils règlent deux points ouverts d'un seul geste. *(a)* La périodicité n'est **pas lisible dans le document** chez trois émetteurs sur quatre — les tokens candidats sont des faux amis (offre commerciale, fenêtre YTD, durée de contrat) : une clé d'appariement ne peut pas reposer sur une valeur indéterminable à la lecture. Complète **O15**. *Conséquence à ne pas perdre (limite LIM5) : la fenêtre sert à **choisir**, jamais à retirer — un ancien profil doit rester vivant pour lire les archives, le run Gronier remontant à 2022.* |
| **D39** | *(2026-07-29)* **Le contexte de marché vit dans une table SÉPARÉE, par période**, partagée par tous les clients — pas dans le store client.
