## Section 1 — Le pipeline sans Excel (amende 1.2 et 1.3 de la v4)

### 1.1 Le rôle de l'Excel — rétrogradé une quatrième et dernière fois

La v3 l'avait rétrogradé trois fois (plus source de vérité ; projection lossy ; hors chemin de
rendu, « ne subsiste que comme surface de rectification CGP »). **La v5 retire ce dernier rôle.**

Le constat est d'usage, pas de principe : l'Excel de transition porte le détail ligne à ligne,
les feuilles de données brutes — **aucun CGP n'ira le modifier**. Et la consultation a un
meilleur endroit : validation_app expose un onglet de consultation du patrimoine plus ergonomique
qu'un classeur. Le README de validation_app l'écrit d'ailleurs lui-même : « *Remplace l'ancien
GUI Excel (`json_to_excel` / `excel_to_store`)* ». **O3 (« drop de l'export Excel — sensible
politiquement ») est clos de fait : le drop a déjà eu lieu côté infra.**

Ce qui survit, et pourquoi :

- **L'Excel de structure** (chantier A) reste l'interface de *collecte initiale* CGP. Il est
  converti **une fois** en JSON à l'entrée du pipeline — c'est une migration, pas un canal.
- **`excel_to_store`** survit comme *convertisseur*, avec deux rôles : la migration one-shot
  ci-dessus, et la **dérivation des stores de vérité** pour les tests du lecteur (§4).
- **`json_to_excel`** (chantier D) perd sa raison d'être produit. La question du rond-trip
  store→excel→store, ouverte la veille, **se dissout** : sans surface de rectification Excel,
  il n'y a pas de ré-ingestion à garantir.
- **Les rectifications de données** passent par le circuit de diff de validation_app
  (`pending/diff_*.json` → revue → apply), jamais par un classeur. C'était déjà D3 ; c'est
  maintenant le *seul* chemin.

### 1.2 L'architecture cible (schéma 1.3 de la v4, amendé)

Le schéma v4 reste juste à une flèche près : la flèche latérale
`writer (json_to_excel vendoré) ──► Excel de transition` **est supprimée**. L'Excel de structure
devient une entrée du convertisseur, au même rang que les PDFs :

```
  Excel de structure (CGP) ──► excel_to_store (validation_app) ──┐   [une fois, à l'entrée]
  PDFs relevés ──► identification (N) ──► extraction ──► diffs ──┤
  XML PENELOP ───────────────────────────────────────────► diffs ┤
                                                                 ▼
                                    apply ──► dict client FORME-STORE (format convergé, D48)
                                                                 │
                                            ├──► store_to_manifest ──► manifeste [J]
                                            └──► lecteur de store ──► listes canoniques [L]
                                                       └──► p2_fill (bank/ figé) ──► HTML
```

**Discipline de bascule (à ne pas négocier)** : le filet de régression actuel — 7 fixtures Excel,
rendu déterministe — protège le chemin Excel→HTML. On ne coupe ce chemin qu'**après** que
l'équivalence store→HTML est prouvée (L3a). La coupure est la récompense du chantier, pas son
premier geste.

### 1.3 Les DEUX Excel du schéma — précision de Thomas, 30/07

Le mot « Excel » recouvre deux artefacts de natures différentes, et la conversion one-shot de
D45 ne vise que le premier :

- **L'Excel de structure** (chantier A, 3 feuilles) est l'**entrée de production** : les ancres
  que le CGP saisit, le moteur attendant le complément par les PDFs. C'est LUI que D45 convertit
  une fois en JSON à l'entrée ; il aura son propre petit convertisseur (3 feuilles → store
  d'ancres), distinct de l'`excel_to_store` de validation_app.
- **Le format riche** (l'Excel de transition, ~15 onglets) ne sert plus qu'à trois choses : les
  **fixtures de test** (c'est lui que `deriver_stores.py` lit pour produire les stores de
  vérité), la **reprise de l'existant** (classeurs riches historiques, via `excel_to_store`
  complété), et la forme qu'aurait un **export** si on en refaisait un — ce que D46 a écarté.

Confondre les deux ferait dimensionner le convertisseur de production sur un format que les CGP
ne rempliront jamais.

## Section 2 — La confrontation des deux stores (fonde D48)

### 2.1 L'état réel de la divergence, constaté le 29/07

Première lecture côte à côte des deux schémas. Ils sont **plus proches qu'on ne le craignait au
sommet, divergents au niveau des entrées** — et la divergence est **bidirectionnelle**, chaque
branche ayant amendé l'ancêtre de son côté :

| | Store fork (`2.0-skill`) | Store émis par validation_app |
|---|---|---|
| Sommet | `liquidites`, `immobilier`, `financier_cote`, `non_cote`, `dettes`, `historique_annuel`, `mouvements`, `valuations` + **`exotiques`** | idem, + **`reference_tables`**, **`courbe_performance`**, `mouvements` |
| Contrat coté | `manager`, `management_mode`, `risk_profile`, `invest_date`, `capital_invested`, `value_jan1`, `value_projected`, `pledged`, `custodian` ; **`attributes.{lines, pockets, ps}`** — poches typées (invariant A5 : `type`, `profile`, `custodian`, `value_jan1`, `invest_date`, `pledged`) | **`assureur`**, **`intermediaire`**, `date_ouverture`, `nantissement`, `contract_label` ; `pockets[]` de premier rang (`classe_rhetores`, `nominal`, `value_current`, `attributes.geography`) |
| Liq / immo / dettes | `genericEntry` **non typé** (id, entity_id, label + audit) — c'était MQ6 | **parseurs typés** : immo (fonction, propriété, hypothèque, loyer, dates, valeurs), dettes (banque, taux, échéance, capital restant, adossement), liq (custodian, solde) |
| Reporting | période + `profile` | période + `profile` + **`blocs_enabled`** |
| Valorisations | `valuations` par position | `valuations` par position + **courbe mensuelle** séparée |
| Audit | `source`, `source_document`, `validated_by`, `validation_note` | idem + verrou optimiste (`version`/`base_version`), `validated_at` |

**L'avertissement qui cadre le chantier** (Thomas, 29/07) : le schéma de validation_app est **plus
ancien** — certaines modifications du fork (les poches typées d'A5, `lines[]`, `ps`) sont
postérieures et n'existent pas en face. La convergence n'est donc **pas une traduction ni une
adoption unilatérale** : c'est une confrontation champ à champ, où chaque écart est arbitré pour
lui-même, dans les deux sens. Le chantier est plus volumineux qu'un renommage.

### 2.2 Ce que la convergence règle d'office

- **MQ1** (assureur/intermédiaire) : le format validation_app les porte au niveau contrat. À
  rapatrier tels quels — codes du **référentiel acteurs** (K), pas texte libre : c'est la
  jointure entre le store client et les référentiels partagés.
- **MQ6** (catégories non typées) : les parseurs typés de validation_app définissent les colonnes ;
  les schémas dédiés du fork s'en dérivent. Plus de `genericEntry` pour liq/immo/dettes.
- ~~**Le logement de `blocs_enabled`** : déjà dans `reporting{}` côté validation_app — le manifeste
  (J) et le store convergent d'eux-mêmes.~~ **Corrigé par la confrontation ①**
  (`confrontation_stores_2026-07-29.md` §1/§5) : ce logement validation_app **contredit** MQ9,
  tranché par la donnée (spec §7.8 — zéro recouvrement store/manifeste). Les commutateurs de rendu
  restent au **manifeste** ; ce que validation_app calcule là est le travail de `store_to_manifest`
  (J1). Le store répond « peut-on ? », pas « veut-on ? ».

Restent à traiter au fil du lecteur (règle L5 : échec bruyant, jamais de défaut silencieux) :
MQ2, MQ3, MQ4, MQ5, MQ7, MQ8, MQ10.

### 2.3 Une incohérence relevée en passant

`excel_to_store.py` émet `schema_version: "1.0"` alors que son docstring et le README parlent du
template **v2.0** de `rhetores_datastore`. À clarifier côté validation_app un jour (O18) — non
bloquant, mais le lecteur du fork ne doit **pas** faire de ce champ un discriminant tant que ce
n'est pas tranché.

## Section 3 — Décisions actées (suite de D44, cf. roadmap)

| # | Décision |
|---|----------|
| D45 | **L'Excel sort du chemin du pipeline.** L'Excel de structure est converti une fois en JSON à l'entrée ; le pipeline entier raisonne en forme-store. Bascule conditionnée à la preuve d'équivalence L3a : on ne coupe pas le chemin Excel→HTML avant que store→HTML soit prouvé équivalent sur les 7 fixtures. |
| D46 | **L'Excel de transition meurt comme surface de rectification et d'export.** Aucun CGP ne modifie un classeur de détail ; la consultation vit dans validation_app, les rectifications de données passent par le circuit de diff (revue → apply), seul chemin. Clôt **O3** (le README de validation_app acte déjà le remplacement du GUI Excel). Le chantier D (writer `json_to_excel`) est **abandonné comme feature produit**. |
| D47 | **On réemploie l'`excel_to_store` de validation_app, on ne le réécrit pas.** Deux rôles : migration one-shot de l'Excel de structure, et dérivation des stores de vérité pour les tests du lecteur. Le dépôt reste en lecture seule : on l'**exécute**, la sortie va dans le fork. Le skill, lui, ne dépend jamais du code de validation_app au runtime — il est autonome hors réseau. |
| D48 | **Convergence des deux forme-stores vers UN format, sous clés françaises, par confrontation champ à champ bidirectionnelle.** Le format `rhetores_datastore` (local_db, source de vérité lue par mcp_fetch et le skill) est le socle ; les amendements du fork postérieurs (poches typées A5, `lines[]`, `ps`) y sont confrontés, pas écrasés — le schéma validation_app étant plus ancien, l'antériorité ne vaut pas canonicité champ à champ. Le lecteur du skill consomme le format convergé. **On vendore le contrat de fichier (schéma), jamais le code.** Résout MQ1 et MQ6 sur le fond (§2.2). Chaque écart arbitré s'inscrit au registre au fil de l'eau (M3). |
| D49 | **Provenance d'extraction sur les entrées du store client.** Toute entrée issue d'un document porte : `source_document` (nom de fichier — légitime *ici*, le store client vit chez le client, contrairement au store partagé où D44 l'interdit), `source_empreinte` (sha256), `source_gabarit` (+ version par fenêtre D42) et `source_arrete`. Deux effets : chaque ligne du store est **auditable** (de quel document, quel gabarit, quelle date elle vient), et le **self-healing ne redéclenche pas d'étude** en relisant une archive — le matcher choisit la version de gabarit par l'arrêté au lieu de crier au drift. Même grammaire que la provenance D44 des adjudications, deux contextes. |

## Section 4 — Chantier L re-scopé (remplace l'ordonnancement de L1–L5, les tâches demeurent)

L'ordre a été arbitré le 29/07 (« excel_to_store d'abord ») ; la découverte de D47 le renforce :
la première brique existe déjà, il n'y a plus rien à écrire avant la confrontation.

| Étape | Contenu | Tâches v4 couvertes |
|---|---|---|
| **① Confrontation des schémas** | Document court : fork vs validation_app, écarts nommés un par un, arbitrage de convergence par écart (D48), entrées au registre. | (fonde tout le reste) |
| **② Stores de vérité** | Exécuter l'`excel_to_store` de validation_app sur les **7 fixtures** ; ajuster vers le format convergé ; ces stores deviennent les fixtures du lecteur. | L1 (généralisé : 7 stores, plus seulement Gronier), L4 |
| **③ Le lecteur** | `skill/pipeline/` : store JSON → listes positionnelles canoniques que `read_sheet` rendait (§3 de la spec du 28/07, ordre canonique sans colmap). Échec bruyant sur tout manque (règle L5). | L2 |
| **④ Preuve L3a** | Harnais : rendu via store ≡ rendu via Excel, égalité exacte, 7 fixtures. Les écarts s'expliquent un par un ou sont des bugs. | L3 (volet fidélité) |
| **⑤ Bascule, puis coupure** | Le chemin store devient le chemin nominal ; la régression bascule sur les fixtures-store ; le chemin Excel est retiré (D45). | (récompense) |

**L3b** (perte réelle de la projection Excel) reste suspendu au store Gronier régénéré depuis les
relevés officiels — inchangé.

## Section 5 — Impacts sur les chantiers de la section 3 (v4)

- **Chantier A** (Excel de structure) : inchangé dans son contenu, recadré dans son rôle —
  c'est l'interface de *collecte*, convertie une fois (D45). A1 reste suspendu à J.
- **Chantier C** (pivot forme-store) : C2/C5 s'exécutent désormais **dans le cadre de D48** — les
  extensions se posent dans le format convergé, pas dans un schéma du fork qui divergerait de plus
  belle. C6 (bloc Contexte) inchangé (D39, table séparée).
- **Chantier D** (writer & Excel de transition) : **abandonné comme feature produit** (D46).
  D1/D2 sans objet ; D3 devient la règle générale (circuit de diff seul chemin de rectification) ;
  D4 (dossier de run archivé, rejouable) **survit** — il ne dépendait pas du writer.
- **Chantier J** (tri des blocs) : le logement de `blocs_enabled` dans `reporting{}` est confirmé
  par validation_app ; c'est aussi la surface sur laquelle la review d'horizon (O17) opérera.
- **Chantier L** : re-scopé en §4 ci-dessus.
- **Registre** : MQ1 et MQ6 sortent de la liste « à poser » via D48 ; leurs entrées au registre se
  font au moment où la forme convergée est posée (M3, au fil de l'eau).
